     1→     1→# Frontend Architecture Specification Prompt
     2→     2→
     3→     3→## Prop Firm as a Service Platform
     4→     4→
     5→     5→You are the lead frontend architect and implementation engineer for a multi-tenant **Prop Firm as a Service (PFaaS)** platform.
     6→     6→
     7→     7→The platform provides white-label infrastructure to multiple prop firms. Each prop firm is a tenant. The platform must support:
     8→     8→
     9→     9→1. Super Admin Dashboard
    10→    10→2. Prop Firm Admin Dashboard
    11→    11→3. Trader/User Dashboard
    12→    12→4. Dynamic, configurable navigation
    13→    13→5. Plug-and-play business modules
    14→    14→6. Tenant-specific module availability
    15→    15→7. Tenant-specific dashboard layouts
    16→    16→8. Tenant-specific branding
    17→    17→9. Role-based access control
    18→    18→10. Feature-level permissions
    19→    19→11. Widget-based dashboards
    20→    20→12. Optional modules such as:
    21→    21→
    22→    22→* Analytics
    23→    23→* Advanced Analytics
    24→    24→* Accounting
    25→    25→* Affiliates
    26→    26→* Marketing
    27→    27→* CRM
    28→    28→* AI / LLM
    29→    29→* KYC / AML
    30→    30→* Notifications
    31→    31→* Support
    32→    32→
    33→    33→13. External integrations that may expose their own frontend capabilities
    34→    34→14. Multiple prop firms using different combinations of services without requiring separate frontend codebases
    35→    35→
    36→    36→The frontend must be designed as a **modular dashboard platform**, not as three independent hard-coded dashboards.
    37→    37→
    38→    38→---
    39→    39→
    40→    40→# 1. PRIMARY OBJECTIVE
    41→    41→
    42→    42→Build a frontend architecture where:
    43→    43→
    44→    44→```text
    45→    45→Tenant
    46→    46→   ↓
    47→    47→Tenant Configuration
    48→    48→   ↓
    49→    49→Tenant Entitlements
    50→    50→   ↓
    51→    51→Enabled Modules
    52→    52→   ↓
    53→    53→Features
    54→    54→   ↓
    55→    55→User Role / Permissions
    56→    56→   ↓
    57→    57→Navigation
    58→    58→   ↓
    59→    59→Routes
    60→    60→   ↓
    61→    61→Dashboard Widgets
    62→    62→   ↓
    63→    63→Rendered UI
    64→    64→```
    65→    65→
    66→    66→The UI must be dynamically composed from these inputs.
    67→    67→
    68→    68→A tenant should be able to have:
    69→    69→
    70→    70→```text
    71→    71→Trading
    72→    72→Challenges
    73→    73→Risk
    74→    74→Payouts
    75→    75→Analytics
    76→    76→```
    77→    77→
    78→    78→while another tenant can have:
    79→    79→
    80→    80→```text
    81→    81→Trading
    82→    82→Challenges
    83→    83→Risk
    84→    84→Payouts
    85→    85→Analytics
    86→    86→Accounting
    87→    87→Affiliates
    88→    88→Marketing
    89→    89→AI
    90→    90→```
    91→    91→
    92→    92→without creating separate frontend applications for each customer.
    93→    93→
    94→    94→The frontend architecture must therefore make **modules first-class citizens**.
    95→    95→
    96→    96→---
    97→    97→
    98→    98→# 2. CORE ARCHITECTURAL PRINCIPLE
    99→    99→
   100→   100→Do NOT build:
   101→   101→
   102→   102→```text
   103→   103→SuperAdminApp
   104→   104→PropFirmAdminApp
   105→   105→TraderApp
   106→   106→```
   107→   107→
   108→   108→as three completely independent applications containing duplicated business UI.
   109→   109→
   110→   110→Instead build:
   111→   111→
   112→   112→```text
   113→   113→Frontend Platform
   114→   114→│
   115→   115→├── Application Shell
   116→   116→├── Module Runtime
   117→   117→├── Module Registry
   118→   118→├── Permission Engine
   119→   119→├── Tenant Context
   120→   120→├── Feature Flag System
   121→   121→├── Theme Engine
   122→   122→├── Navigation Engine
   123→   123→├── Layout Engine
   124→   124→├── Widget Engine
   125→   125→├── Routing Engine
   126→   126→├── UI Component Library
   127→   127→└── API Client Layer
   128→   128→```
   129→   129→
   130→   130→Then expose role-specific experiences:
   131→   131→
   132→   132→```text
   133→   133→Super Admin Experience
   134→   134→Prop Firm Admin Experience
   135→   135→Trader Experience
   136→   136→```
   137→   137→
   138→   138→using the same platform foundations.
   139→   139→

   142→   142→# 3. RECOMMENDED TECHNOLOGY
   143→   143→
   144→   144→Use:
   145→   145→
   146→   146→```text
   147→   147→Next.js
   148→   148→TypeScript
   149→   149→React
   150→   150→Tailwind CSS
   151→   151→shadcn/ui
   152→   152→React Query / TanStack Query
   153→   153→React Hook Form
   154→   154→Zod
   155→   155→```
   156→   156→
   157→   157→Use the existing project conventions if the repository already has a frontend stack.
   158→   158→
   159→   159→Do NOT introduce unnecessary technologies.
   160→   160→
   161→   161→Avoid:
   162→   162→
   163→   163→```text
   164→   164→Micro-frontends
   165→   165→Webpack Module Federation
   166→   166→GraphQL
   167→   167→Redux
   168→   168→Complex state-management frameworks
   169→   169→Multiple UI libraries
   170→   170→```
   171→   171→
   172→   172→unless there is a concrete existing requirement for them.
   173→   173→
   174→   174→Prefer:
   175→   175→
   176→   176→```text
   177→   177→React Server Components where appropriate
   178→   178→Client Components only when necessary
   179→   179→TanStack Query for server state
   180→   180→React Context for small cross-cutting client state
   181→   181→URL state for filters/search/pagination where appropriate
   182→   182→```

   260→   260→# 5. APPLICATIONS
   261→   261→
   262→   262→There should be three frontend applications or three clearly separated application entry points:
   263→   263→
   264→   264→```text
   265→   265→apps/
   266→   266→├── super-admin/
   267→   267→├── prop-admin/
   268→   268→└── trader/

   271→   271→They should all consume the same shared packages and modules.
   272→   272→
   273→   273→The applications should primarily define:
   274→   274→

   280→   280→experience-specific access rules

   282→   282→
   283→   283→They should NOT duplicate:
   284→   284→
   285→   285→```text
   286→   286→table components
   287→   287→charts
   288→   288→buttons
   289→   289→forms
   290→   290→module logic
   291→   291→permission logic
   292→   292→API abstractions
   293→   293→tenant handling
   294→   294→theme handling
   295→   295→dashboard engine
   296→   296→```

   351→   351→# 7. PROP FIRM ADMIN APPLICATION
   352→   352→
   353→   353→The Prop Firm Admin controls an individual tenant.
   354→   354→
   355→   355→Typical modules:
   356→   356→
   357→   357→```text
   358→   358→Overview
   359→   359→Traders
   360→   360→Trading Accounts
   361→   361→Challenges
   362→   362→Rules
   363→   363→Risk
   364→   364→Breaches
   365→   365→Payouts
   366→   366→Affiliates
   367→   367→Marketing
   368→   368→Analytics
   369→   369→Accounting
   370→   370→AI
   371→   371→Support
   372→   372→Notifications
   373→   373→Settings
   374→   374→```
   375→   375→
   376→   376→But the sidebar must NOT hard-code all modules.
   377→   377→
   378→   378→Instead:
   379→   379→
   380→   380→```text
   381→   381→Tenant Entitlements
   382→   382→        ↓
   383→   383→Module Registry
   384→   384→        ↓
   385→   385→Permission Evaluation

   393→   393→
   394→   394→```text
   395→   395→Accounting
   396→   396→```
   397→   397→
   398→   398→A tenant with Accounting enabled but without:
   399→   399→
   400→   400→```text
   401→   401→accounting.read
   402→   402→```
   403→   403→
   404→   404→must also not see it.

   495→   495→  name: string;

   525→   525→

   527→   527→
   528→   528→Example:
   529→   529→
   530→   530→```typescript
   531→   531→type AuthUser = {

   533→   533→  tenantId?: string;
   534→   534→
   535→   535→  name: string;
   536→   536→  email: string;
   537→   537→
   538→   538→  roles: string[];
   539→   539→  permissions: string[];
   540→   540→};
   541→   541→```
   542→   542→
   543→   543→Expose:
   544→   544→

   556→   556→
   557→   557→# 12. AUTHORIZATION MODEL
   558→   558→
   559→   559→Do not rely only on role names.
   560→   560→
   561→   561→Use explicit permissions.
   562→   562→
   563→   563→Examples:
   564→   564→
   565→   565→```text
   566→   566→trader.read
   567→   567→trader.update
   568→   568→
   569→   569→account.read
   570→   570→account.write
   571→   571→
   572→   572→challenge.read
   573→   573→challenge.create
   574→   574→challenge.update
   575→   575→challenge.delete
   576→   576→
   577→   577→risk.read
   578→   578→risk.configure
   579→   579→
   580→   580→payout.read
   581→   581→payout.approve
   582→   582→
   583→   583→analytics.read
   584→   584→analytics.advanced.read
   585→   585→analytics.export
   586→   586→
   587→   587→affiliate.read
   588→   588→affiliate.configure
   589→   589→
   590→   590→accounting.read
   591→   591→accounting.configure
   592→   592→
   593→   593→ai.read
   594→   594→ai.configure
   595→   595→```
   596→   596→
   597→   597→Create reusable authorization utilities:
   598→   598→
   599→   599→```typescript
   600→   600→can(permission)
   601→   601→hasRole(role)
   602→   602→hasAnyPermission(...)
   603→   603→hasAllPermissions(...)
   604→   604→```
   605→   605→
   606→   606→Example:
   607→   607→
   608→   608→```typescript
   609→   609→if (can("analytics.export")) {
   610→   610→  ...
   611→   611→}
   612→   612→```
   613→   613→
   614→   614→Avoid arbitrary role checks throughout the UI.
   615→   615→
   616→   616→Bad:
   617→   617→
   618→   618→```typescript
   619→   619→if (user.role === "admin") ...
   620→   620→```
   621→   621→
   622→   622→Prefer:
   623→   623→
   624→   624→```typescript
   625→   625→if (can("analytics.export")) ...
   626→   626→```
   627→   627→
   628→   628→Roles should map to permissions.
   629→   629→

   636→   636→Each module should have a manifest.

   638→   638→Example:
   639→   639→
   640→   640→```typescript
   641→   641→type FrontendModuleManifest = {
   642→   642→  id: string;
   643→   643→  name: string;
   644→   644→  version: string;
   645→   645→
   646→   646→  description?: string;
   647→   647→
   648→   648→  dependencies?: string[];
   649→   649→
   650→   650→  capabilities?: string[];
   651→   651→
   652→   652→  permissions?: PermissionDefinition[];
   653→   653→
   654→   654→  navigation?: NavigationDefinition[];
   655→   655→
   656→   656→  routes?: RouteDefinition[];
   657→   657→
   658→   658→  widgets?: WidgetDefinition[];
   659→   659→
   660→   660→  settings?: SettingDefinition[];
   661→   661→
   662→   662→  supportedApplications?: (
   663→   663→    "super-admin" |
   664→   664→    "prop-admin" |
   665→   665→    "trader"
   666→   666→  )[];

   668→   668→```
   669→   669→
   670→   670→Example:
   671→   671→

   678→   678→  dependencies: [

   680→   680→    "accounts"
   681→   681→  ],
   682→   682→
   683→   683→  permissions: [
   684→   684→    "analytics.read",
   685→   685→    "analytics.export"
   686→   686→  ],
   687→   687→
   688→   688→  supportedApplications: [
   689→   689→    "prop-admin",
   690→   690→    "super-admin"
   691→   691→  ]
   692→   692→};
   693→   693→```
