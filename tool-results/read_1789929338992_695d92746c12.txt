     1→# Frontend Architecture Specification Prompt
     2→
     3→## Prop Firm as a Service Platform
     4→
     5→You are the lead frontend architect and implementation engineer for a multi-tenant **Prop Firm as a Service (PFaaS)** platform.
     6→
     7→The platform provides white-label infrastructure to multiple prop firms. Each prop firm is a tenant. The platform must support:
     8→
     9→1. Super Admin Dashboard
    10→2. Prop Firm Admin Dashboard
    11→3. Trader/User Dashboard
    12→4. Dynamic, configurable navigation
    13→5. Plug-and-play business modules
    14→6. Tenant-specific module availability
    15→7. Tenant-specific dashboard layouts
    16→8. Tenant-specific branding
    17→9. Role-based access control
    18→10. Feature-level permissions
    19→11. Widget-based dashboards
    20→12. Optional modules such as:
    21→
    22→* Analytics
    23→* Advanced Analytics
    24→* Accounting
    25→* Affiliates
    26→* Marketing
    27→* CRM
    28→* AI / LLM
    29→* KYC / AML
    30→* Notifications
    31→* Support
    32→
    33→13. External integrations that may expose their own frontend capabilities
    34→14. Multiple prop firms using different combinations of services without requiring separate frontend codebases
    35→
    36→The frontend must be designed as a **modular dashboard platform**, not as three independent hard-coded dashboards.
    37→
    38→---
    39→
    40→# 1. PRIMARY OBJECTIVE
    41→
    42→Build a frontend architecture where:
    43→
    44→```text
    45→Tenant
    46→   ↓
    47→Tenant Configuration
    48→   ↓
    49→Tenant Entitlements
    50→   ↓
    51→Enabled Modules
    52→   ↓
    53→Features
    54→   ↓
    55→User Role / Permissions
    56→   ↓
    57→Navigation
    58→   ↓
    59→Routes
    60→   ↓
    61→Dashboard Widgets
    62→   ↓
    63→Rendered UI
    64→```
    65→
    66→The UI must be dynamically composed from these inputs.
    67→
    68→A tenant should be able to have:
    69→
    70→```text
    71→Trading
    72→Challenges
    73→Risk
    74→Payouts
    75→Analytics
    76→```
    77→
    78→while another tenant can have:
    79→
    80→```text
    81→Trading
    82→Challenges
    83→Risk
    84→Payouts
    85→Analytics
    86→Accounting
    87→Affiliates
    88→Marketing
    89→AI
    90→```
    91→
    92→without creating separate frontend applications for each customer.
    93→
    94→The frontend architecture must therefore make **modules first-class citizens**.
    95→
    96→---
    97→
    98→# 2. CORE ARCHITECTURAL PRINCIPLE
    99→
   100→Do NOT build:
   101→
   102→```text
   103→SuperAdminApp
   104→PropFirmAdminApp
   105→TraderApp
   106→```
   107→
   108→as three completely independent applications containing duplicated business UI.
   109→
   110→Instead build:
   111→
   112→```text
   113→Frontend Platform
   114→│
   115→├── Application Shell
   116→├── Module Runtime
   117→├── Module Registry
   118→├── Permission Engine
   119→├── Tenant Context
   120→├── Feature Flag System
   121→├── Theme Engine
   122→├── Navigation Engine
   123→├── Layout Engine
   124→├── Widget Engine
   125→├── Routing Engine
   126→├── UI Component Library
   127→└── API Client Layer
   128→```
   129→
   130→Then expose role-specific experiences:
   131→
   132→```text
   133→Super Admin Experience
   134→Prop Firm Admin Experience
   135→Trader Experience
   136→```
   137→
   138→using the same platform foundations.
   139→
   140→---
   141→
   142→# 3. RECOMMENDED TECHNOLOGY
   143→
   144→Use:
   145→
   146→```text
   147→Next.js
   148→TypeScript
   149→React
   150→Tailwind CSS
   151→shadcn/ui
   152→React Query / TanStack Query
   153→React Hook Form
   154→Zod
   155→```
   156→
   157→Use the existing project conventions if the repository already has a frontend stack.
   158→
   159→Do NOT introduce unnecessary technologies.
   160→
   161→Avoid:
   162→
   163→```text
   164→Micro-frontends
   165→Webpack Module Federation
   166→GraphQL
   167→Redux
   168→Complex state-management frameworks
   169→Multiple UI libraries
   170→```
   171→
   172→unless there is a concrete existing requirement for them.
   173→
   174→Prefer:
   175→
   176→```text
   177→React Server Components where appropriate
   178→Client Components only when necessary
   179→TanStack Query for server state
   180→React Context for small cross-cutting client state
   181→URL state for filters/search/pagination where appropriate
   182→```

   260→# 5. APPLICATIONS
   261→
   262→There should be three frontend applications or three clearly separated application entry points:
   263→
   264→```text
   265→apps/
   266→├── super-admin/
   267→├── prop-admin/
   268→└── trader/
   269→```
   270→
   271→They should all consume the same shared packages and modules.
   272→
   273→The applications should primarily define:
   274→
   275→```text
   276→authentication entry
   277→route entry points
   278→application-level layout
   279→experience-specific navigation defaults
   280→experience-specific access rules
   281→```
   282→
   283→They should NOT duplicate:
   284→
   285→```text
   286→table components
   287→charts
   288→buttons
   289→forms
   290→module logic
   291→permission logic
   292→API abstractions
   293→tenant handling
   294→theme handling
   295→dashboard engine
   296→```

   318→Billing
   319→Audit Logs
   320→Platform Analytics
   321→System Health
   322→Platform Settings
   323→```

   325→Recommended structure:
   326→
   327→```text
   328→apps/super-admin/
   329→│
   330→├── app/
   331→│   ├── (auth)/
   332→│   └── (dashboard)/

   334→│       ├── page.tsx

   347→The Super Admin should also use the same module system.

   351→# 7. PROP FIRM ADMIN APPLICATION
   352→
   353→The Prop Firm Admin controls an individual tenant.
   354→
   355→Typical modules:
   356→
   357→```text
   358→Overview
   359→Traders
   360→Trading Accounts
   361→Challenges
   362→Rules
   363→Risk
   364→Breaches
   365→Payouts
   366→Affiliates
   367→Marketing
   368→Analytics
   369→Accounting
   370→AI
   371→Support
   372→Notifications
   373→Settings
   374→```
   375→
   376→But the sidebar must NOT hard-code all modules.
   377→
   378→Instead:
   379→
   380→```text
   381→Tenant Entitlements
   382→        ↓
   383→Module Registry
   384→        ↓
   385→Permission Evaluation
   386→        ↓
   387→Navigation Registry
   388→        ↓
   389→Dynamic Sidebar
   390→```
   391→
   392→For example, a tenant with no Accounting entitlement must not see:
   393→
   394→```text
   395→Accounting
   396→```
   397→
   398→A tenant with Accounting enabled but without:
   399→
   400→```text
   401→accounting.read
   402→```
   403→
   404→must also not see it.

   438→user permissions
   439→feature flags

   441→```

   452→

   464→The shell should support:
   465→
   466→```text

   468→Collapsible sidebar
   469→Mobile navigation

   471→Global search
   472→Notifications
   473→User menu
   474→Tenant switcher where applicable
   475→Theme switcher
   476→Command menu
   477→Page actions
   478→Persistent navigation state
   479→```
   480→
   481→The Shell should be independent of business modules.

   485→# 10. TENANT CONTEXT
   486→
   487→Create a reusable Tenant Context.
   488→
   489→Example:
   490→
   491→```typescript
   492→type TenantContext = {
   493→  tenantId: string;
   494→  slug: string;
   495→  name: string;
   496→
   497→  branding: TenantBranding;
   498→
   499→  locale: string;
   500→  timezone: string;
   501→  currency: string;
   502→
   503→  enabledModules: string[];
   504→  enabledFeatures: string[];
   505→
   506→  terminology: Record<string, string>;
   507→};
   508→```
   509→
   510→The frontend must retrieve and expose tenant context centrally.
   511→
   512→Example:
   513→
   514→```text
   515→TenantProvider
   516→      ↓
   517→useTenant()
   518→```
   519→
   520→Components should not repeatedly request tenant configuration independently.
   521→

   523→
   524→# 11. AUTHENTICATION CONTEXT
   525→
   526→Create a reusable authentication layer.
   527→
   528→Example:
   529→
   530→```typescript
   531→type AuthUser = {
   532→  id: string;
   533→  tenantId?: string;
   534→
   535→  name: string;
   536→  email: string;
   537→
   538→  roles: string[];
   539→  permissions: string[];
   540→};
   541→```
   542→
   543→Expose:
   544→
   545→```text
   546→useAuth()
   547→useCurrentUser()
   548→useCurrentTenant()
   549→```
   550→
   551→The exact implementation may depend on the authentication provider.
   552→
   553→Do not couple the dashboard architecture to a specific auth provider.
   554→
   555→---
   556→
   557→# 12. AUTHORIZATION MODEL
   558→
   559→Do not rely only on role names.
   560→
   561→Use explicit permissions.
   562→
   563→Examples:
   564→
   565→```text
   566→trader.read
   567→trader.update
   568→
   569→account.read
   570→account.write
   571→
   572→challenge.read
   573→challenge.create
   574→challenge.update
   575→challenge.delete
   576→
   577→risk.read
   578→risk.configure
   579→
   580→payout.read
   581→payout.approve
   582→
   583→analytics.read
   584→analytics.advanced.read
   585→analytics.export
   586→
   587→affiliate.read
   588→affiliate.configure
   589→
   590→accounting.read
   591→accounting.configure
   592→
   593→ai.read
   594→ai.configure
   595→```
   596→
   597→Create reusable authorization utilities:
   598→
   599→```typescript
   600→can(permission)
   601→hasRole(role)
   602→hasAnyPermission(...)
   603→hasAllPermissions(...)
   604→```
   605→
   606→Example:
   607→
   608→```typescript
   609→if (can("analytics.export")) {
   610→  ...
   611→}
   612→```
   613→
   614→Avoid arbitrary role checks throughout the UI.
   615→
   616→Bad:
   617→
   618→```typescript
   619→if (user.role === "admin") ...
   620→```
   621→
   622→Prefer:
   623→
   624→```typescript
   625→if (can("analytics.export")) ...
   626→```
   627→
   628→Roles should map to permissions.
   629→

   632→# 13. MODULE SYSTEM
   633→
   634→Implement a first-class module registry.
   635→
   636→Each module should have a manifest.
   637→
   638→Example:
   639→
   640→```typescript
   641→type FrontendModuleManifest = {
   642→  id: string;
   643→  name: string;
   644→  version: string;
   645→
   646→  description?: string;
   647→
   648→  dependencies?: string[];
   649→
   650→  capabilities?: string[];
   651→
   652→  permissions?: PermissionDefinition[];
   653→
   654→  navigation?: NavigationDefinition[];
   655→
   656→  routes?: RouteDefinition[];
   657→
   658→  widgets?: WidgetDefinition[];
   659→
   660→  settings?: SettingDefinition[];
   661→
   662→  supportedApplications?: (
   663→    "super-admin" |
   664→    "prop-admin" |
   665→    "trader"
   666→  )[];
   667→};
   668→```
   669→
   670→Example:
   671→
   672→```typescript
   673→const analyticsModule: FrontendModuleManifest = {
   674→  id: "analytics",
   675→  name: "Analytics",
   676→  version: "1.0.0",
   677→
   678→  dependencies: [
   679→    "trading",
   680→    "accounts"
   681→  ],
   682→
   683→  permissions: [
   684→    "analytics.read",
   685→    "analytics.export"
   686→  ],
   687→
   688→  supportedApplications: [
   689→    "prop-admin",
   690→    "super-admin"
   691→  ]
   692→};
   693→```

   746→# 15. MODULE REGISTRY
   747→
   748→Create:
   749→
   750→```text
   751→packages/module-sdk/
   752→```
   753→
   754→with something conceptually like:
   755→
   756→```typescript
   757→class ModuleRegistry {
   758→  register(module: FrontendModuleManifest): void;
   759→
   760→  get(moduleId: string): FrontendModuleManifest | undefined;
   761→
   762→  getAll(): FrontendModuleManifest[];
   763→
   764→  getEnabledModules(context: ModuleRuntimeContext): FrontendModuleManifest[];
   765→
   766→  getNavigation(context: ModuleRuntimeContext): NavigationItem[];
   767→
   768→  getWidgets(context: ModuleRuntimeContext): WidgetDefinition[];
   769→}
   770→```
   771→
   772→The registry is the central source of module metadata.
   773→

   775→
   776→# 16. MODULE RUNTIME
   777→
   778→Create a runtime layer responsible for determining:
   779→
   780→```text
   781→Which modules exist?
   782→Which modules are enabled?
   783→Which modules are available to this application?
   784→Which features are enabled?
   785→Which permissions does the current user have?
   786→Which routes should exist?
   787→Which navigation items should appear?
   788→Which widgets should render?
   789→```
   790→
   791→Conceptually:
   792→
   793→```text
   794→Module Runtime
   795→│
   796→├── Module Discovery
   797→├── Module Availability
   798→├── Dependency Validation
   799→├── Entitlement Filtering
   800→├── Permission Filtering
   801→├── Feature Flag Filtering
   802→└── Runtime Composition
   803→```
   804→

   806→
   807→# 17. NAVIGATION ENGINE
   808→
   809→The sidebar must be generated dynamically.
   810→
   811→Do NOT create one giant static sidebar file.
   812→
   813→Instead each module can register navigation:
   814→
   815→```typescript
   816→const navigation = [
   817→  {
   818→    id: "analytics",
   819→    label: "Analytics",
   820→    href: "/analytics",
   821→    icon: ChartIcon,
   822→    permission: "analytics.read"
   823→  }
   824→];
   825→```
   826→
   827→The navigation engine should combine:
   828→
   829→```text
   830→Core Navigation
   831→+
   832→Module Navigation
   833→+
   834→Tenant Configuration
   835→+
   836→Permissions
   837→+
   838→Feature Flags
   839→```
   840→
   841→Then generate the final sidebar.
   842→

   846→
   847→Support hierarchical navigation.
   848→
   849→Example:
   850→

   866→  href?: string;

   870→  permission?: string;
   871→  permissions?: string[];
   872→
   873→  feature?: string;
   874→  module?: string;
   875→};
   876→```

   879→
   880→# 19. ROUTING
   881→
   882→Routes must be module-oriented.
   883→
   884→Example:
   885→
   886→```text
   887→/analytics
   888→/analytics/traders
   889→/analytics/performance
   890→/analytics/risk
   891→
   892→/accounting
   893→/accounting/transactions
   894→/accounting/reconciliation
   895→
   896→/affiliates
   897→/affiliates/overview
   898→/affiliates/campaigns
   899→/affiliates/commissions
   900→```
   901→
   902→The frontend should protect routes using:
   903→
   904→```text
   905→Authentication
   906→Tenant
   907→Module entitlement
   908→Feature flag
   909→Permission
   910→```
   911→
   912→A user must not be able to access an unavailable module simply by manually typing its URL.
   913→
   914→Example:
   915→
   916→```text
   917→/analytics
   918→```
   919→
   920→must not load when:
   921→
   922→```text
   923→analytics
   924→```
