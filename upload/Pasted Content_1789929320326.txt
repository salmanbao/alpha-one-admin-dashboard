# Frontend Architecture Specification Prompt

## Prop Firm as a Service Platform

You are the lead frontend architect and implementation engineer for a multi-tenant **Prop Firm as a Service (PFaaS)** platform.

The platform provides white-label infrastructure to multiple prop firms. Each prop firm is a tenant. The platform must support:

1. Super Admin Dashboard
2. Prop Firm Admin Dashboard
3. Trader/User Dashboard
4. Dynamic, configurable navigation
5. Plug-and-play business modules
6. Tenant-specific module availability
7. Tenant-specific dashboard layouts
8. Tenant-specific branding
9. Role-based access control
10. Feature-level permissions
11. Widget-based dashboards
12. Optional modules such as:

* Analytics
* Advanced Analytics
* Accounting
* Affiliates
* Marketing
* CRM
* AI / LLM
* KYC / AML
* Notifications
* Support

13. External integrations that may expose their own frontend capabilities
14. Multiple prop firms using different combinations of services without requiring separate frontend codebases

The frontend must be designed as a **modular dashboard platform**, not as three independent hard-coded dashboards.

---

# 1. PRIMARY OBJECTIVE

Build a frontend architecture where:

```text
Tenant
   ↓
Tenant Configuration
   ↓
Tenant Entitlements
   ↓
Enabled Modules
   ↓
Features
   ↓
User Role / Permissions
   ↓
Navigation
   ↓
Routes
   ↓
Dashboard Widgets
   ↓
Rendered UI
```

The UI must be dynamically composed from these inputs.

A tenant should be able to have:

```text
Trading
Challenges
Risk
Payouts
Analytics
```

while another tenant can have:

```text
Trading
Challenges
Risk
Payouts
Analytics
Accounting
Affiliates
Marketing
AI
```

without creating separate frontend applications for each customer.

The frontend architecture must therefore make **modules first-class citizens**.

---

# 2. CORE ARCHITECTURAL PRINCIPLE

Do NOT build:

```text
SuperAdminApp
PropFirmAdminApp
TraderApp
```

as three completely independent applications containing duplicated business UI.

Instead build:

```text
Frontend Platform
│
├── Application Shell
├── Module Runtime
├── Module Registry
├── Permission Engine
├── Tenant Context
├── Feature Flag System
├── Theme Engine
├── Navigation Engine
├── Layout Engine
├── Widget Engine
├── Routing Engine
├── UI Component Library
└── API Client Layer
```

Then expose role-specific experiences:

```text
Super Admin Experience
Prop Firm Admin Experience
Trader Experience
```

using the same platform foundations.

---

# 3. RECOMMENDED TECHNOLOGY

Use:

```text
Next.js
TypeScript
React
Tailwind CSS
shadcn/ui
React Query / TanStack Query
React Hook Form
Zod
```

Use the existing project conventions if the repository already has a frontend stack.

Do NOT introduce unnecessary technologies.

Avoid:

```text
Micro-frontends
Webpack Module Federation
GraphQL
Redux
Complex state-management frameworks
Multiple UI libraries
```

unless there is a concrete existing requirement for them.

Prefer:

```text
React Server Components where appropriate
Client Components only when necessary
TanStack Query for server state
React Context for small cross-cutting client state
URL state for filters/search/pagination where appropriate
```

# 5. APPLICATIONS

There should be three frontend applications or three clearly separated application entry points:

```text
apps/
├── super-admin/
├── prop-admin/
└── trader/
```

They should all consume the same shared packages and modules.

The applications should primarily define:

```text
authentication entry
route entry points
application-level layout
experience-specific navigation defaults
experience-specific access rules
```

They should NOT duplicate:

```text
table components
charts
buttons
forms
module logic
permission logic
API abstractions
tenant handling
theme handling
dashboard engine
```

# 12. AUTHORIZATION MODEL

Do not rely only on role names.

Use explicit permissions.

Examples:

```text
trader.read
trader.update

account.read
account.write

challenge.read
challenge.create
challenge.update
challenge.delete

risk.read
risk.configure

payout.read
payout.approve

analytics.read
analytics.advanced.read
analytics.export

affiliate.read
affiliate.configure

accounting.read
accounting.configure

ai.read
ai.configure
```

Create reusable authorization utilities:

```typescript
can(permission)
hasRole(role)
hasAnyPermission(...)
hasAllPermissions(...)
```

Example:

```typescript
if (can("analytics.export")) {
  ...
}
```

Avoid arbitrary role checks throughout the UI.

Bad:

```typescript
if (user.role === "admin") ...
```

Prefer:

```typescript
if (can("analytics.export")) ...
```

Roles should map to permissions.

# 13. MODULE SYSTEM

Implement a first-class module registry.

Each module should have a manifest.

Example:

```typescript
type FrontendModuleManifest = {
  id: string;
  name: string;
  version: string;

  description?: string;

  dependencies?: string[];

  capabilities?: string[];

  permissions?: PermissionDefinition[];

  navigation?: NavigationDefinition[];

  routes?: RouteDefinition[];

  widgets?: WidgetDefinition[];

  settings?: SettingDefinition[];

  supportedApplications?: (
    "super-admin" |
    "prop-admin" |
    "trader"
  )[];
};
```

Example:

```typescript
const analyticsModule: FrontendModuleManifest = {
  id: "analytics",
  name: "Analytics",
  version: "1.0.0",

  dependencies: [
    "trading",
    "accounts"
  ],

  permissions: [
    "analytics.read",
    "analytics.export"
  ],

  supportedApplications: [
    "prop-admin",
    "super-admin"
  ]
};
```

# 15. MODULE REGISTRY

Create:

```text
packages/module-sdk/
```

with something conceptually like:

```typescript
class ModuleRegistry {
  register(module: FrontendModuleManifest): void;

  get(moduleId: string): FrontendModuleManifest | undefined;

  getAll(): FrontendModuleManifest[];

  getEnabledModules(context: ModuleRuntimeContext): FrontendModuleManifest[];

  getNavigation(context: ModuleRuntimeContext): NavigationItem[];

  getWidgets(context: ModuleRuntimeContext): WidgetDefinition[];
}
```

The registry is the central source of module metadata.

# 17. NAVIGATION ENGINE

The sidebar must be generated dynamically.

Do NOT create one giant static sidebar file.

Instead each module can register navigation:

```typescript
const navigation = [
  {
    id: "analytics",
    label: "Analytics",
    href: "/analytics",
    icon: ChartIcon,
    permission: "analytics.read"
  }
];
```

The navigation engine should combine:

```text
Core Navigation
+
Module Navigation
+
Tenant Configuration
+
Permissions
+
Feature Flags
```

Then generate the final sidebar.

# 22. DASHBOARD LAYOUT CONFIGURATION

Do not hard-code widget positions.

Represent layouts as configuration.

Example:

```typescript
type DashboardLayout = {
  id: string;
  tenantId?: string;

  widgets: DashboardWidgetPlacement[];
};

type DashboardWidgetPlacement = {
  widgetId: string;

  x: number;
  y: number;

  width: number;
  height: number;

  minWidth?: number;
  minHeight?: number;
};
```

Allow:

```text
Platform default layout
       ↓
Tenant layout
       ↓
Role-specific layout
       ↓
User custom layout
```

The exact priority must be clearly defined.

Recommended:

```text
User customization
    >
Role layout
    >
Tenant layout
    >
Platform default
```

# 33. DO NOT TRUST FRONTEND AUTHORIZATION

Frontend guards are for UX.

They are NOT a security boundary.

The frontend architecture should assume the backend independently enforces:

```text
authentication
authorization
tenant isolation
resource access
```

Do not implement security by hiding buttons.

---

# 34. ERROR BOUNDARIES

Each module should have its own error boundary.

Example:

```text
Analytics Module
      ↓
AnalyticsErrorBoundary
```

If Analytics crashes, the entire admin dashboard should not crash.

The shell should remain operational.

Display:

```text
Something went wrong loading Analytics.
Retry
```

rather than blanking the entire application.

# 74. ACCEPTANCE CRITERIA

The frontend architecture is considered successful only when all of the following work:

### Tenant isolation

A user can only operate inside the tenant context they are authorized for.

### Dynamic modules

A disabled module produces no accessible navigation or route.

### Permissions

A user without permission cannot access protected UI or routes.

### Dashboard composition

Dashboard widgets can be added, removed, moved, and resized through configuration.

### White labeling

Tenant branding can be applied without a separate frontend build.

### Module independence

A module can own:

```text
pages
components
routes
navigation
widgets
API hooks
permissions
```

without spreading its business logic throughout the application.

### Shared platform

Super Admin, Prop Firm Admin, and Trader applications reuse:

```text
UI
authorization
theme
tenant
module registry
dashboard infrastructure
API patterns
```

### No tenant-specific hacks

There should be no architecture such as:

```typescript
if (tenantId === "tenantA")
```

for standard product behavior.

### Optional services

Adding a new module such as:

```text
Accounting
```

should require registering the module and its capabilities, not rewriting the entire dashboard.

# 76. ENGINEERING PHILOSOPHY

The frontend should follow this rule:

```text
Core Platform
    owns composition

Modules
    own domain functionality

Configuration
    controls variation

Permissions
    control access

Tenant
    controls customization

Widgets
    provide dashboard composition

Shared UI
    provides visual consistency
```

The frontend should feel like one coherent platform while internally behaving like a collection of independently developed business modules.

The final result must be capable of evolving from:

```text
5 modules
```

to:

```text
20+ modules
```

without turning the frontend into a large collection of tenant-specific conditionals and duplicated dashboard implementations.
